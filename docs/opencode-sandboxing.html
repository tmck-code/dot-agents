OpenCode sandboxing: audit & options

What the current Docker image actually protects, where it stops being a boundary, and how Docker Sandboxes, microVMs, hardened containers and OpenCode’s own controls compare. Written for a developer who already has an image and wants to run agents without gambling the host.

27 October 2026 tmck-code/dot-agents OpenCode 2.1.4 · Docker Engine / Desktop 15 findings · 5 diagrams
Verdict

The current image is a good developer environment, not a security boundary.

It gives you a non-root user, a real toolchain, and a familiar workflow, but it shares a kernel (the host’s on Linux, Docker Desktop’s VM on macOS and Windows), mounts host config and credentials, and has no egress control. If the goal is safely running untrusted repos or autonomous agents, Docker Sandboxes (sbx) or another microVM is the correct boundary. If the goal is running your dotfiles on trusted repos, harden this image rather than abandoning it.

A container is a namespace boundary, not a hypervisor boundary. Permission prompts inside OpenCode are UX, not isolation.

02Threat model

What you are actually protecting

The assets are the repo and its worktree, provider API keys, the GitHub OAuth token, SSH private keys, cloud credentials, databases and services on the host LAN, and the host config directories the agent can read or write. The adversary is rarely a cinematic attacker: it is prompt injection in an issue, README or dependency; a malicious repo; a project .opencode/plugin; a compromised model or provider; or simply an over-broad agent command that deletes the wrong tree or pushes the wrong branch.

The goal is to contain blast radius, keep real credentials out of the agent’s reach, keep egress narrow, and preserve auditability. OpenCode’s own security documentation is explicit that it does not sandbox the agent; its approval prompts are a human workflow, not a kernel boundary. Any protection that depends on the agent choosing to obey a rule is policy, not isolation.

Assets

Crown jewels

Repo + worktree; provider keys; GitHub token; SSH keys and agent socket; cloud creds; database DSNs; host LAN services (Ollama, Postgres, dev servers); ~/.claude, ~/.config/opencode, auth.json.

Adversary

Untrusted input

Prompt injection; malicious dependency or repo; attacker-authored project plugin, skill or AGENTS.md; compromised provider; an over-eager agent command; a kernel or runtime escape from a compromised workload.

Goal

Containment

Minimum host data in the trust domain; no long-lived secrets inside it; deny-by-default egress; a real kernel/VM boundary for untrusted work; logs that survive the session; a repeatable rebuild path.

The one-sentence version

A shared-kernel container with your SSH keys, GitHub token and unrestricted network is an organisational control (“please do not do that”), not a technical boundary. Use it for trusted code, and move the boundary outside the agent when the code is not trusted.

03Current approach · audit

The Docker image, line by line

This audits docker/opencode/run.sh and docker/opencode/Dockerfile as they exist in the repo. References are to those files. The engineering is competent and deliberate; the findings are about what the design cannot do, not about sloppiness.

Showing 15 of 15
Critical

No egress policy

run.sh:75, 130–134, 114–117

What the code does run.sh builds a plain docker run --rm --init with no --network flag, so the container lands on Docker’s default bridge. Lines 132–134 add host.docker.internal:host-gateway on Linux, and OPENCODE_DOCKER_ARGS (line 114) lets a caller add --network=host. Nothing restricts destinations.

Why it matters A prompt-injected or malicious command can reach the internet, your LAN, host services (Ollama, databases, dev servers) and, where the host permits it, cloud metadata endpoints. The only limit is what the host network exposes. Combined with readable credentials, this is a complete exfiltration path.

Fix Put the container on an --internal network with a filtering egress proxy as the only route out; allowlist provider and registry hostnames. Drop host.docker.internal unless a specific host service is needed, and gate --network=host behind an explicit unsafe flag.

Critical

Host credentials are inside the trust domain

run.sh:171–179, 188–208, 229–244, 276–287

What the code does Mounts ~/.ssh read-only, forwards $SSH_AUTH_SOCK on Linux, mounts ~/.config/gh read-only, ~/.gitconfig, and ~/.local/share/opencode (including auth.json), and forwards provider/GitHub env vars by name.

Why it matters Any process in the container can read the private keys and tokens. Read-only prevents writes, not exfiltration. The SSH agent is worse than a key file in one respect: while loaded, it will sign a challenge for any host the network allows, not just GitHub. The README says this plainly; the default path still does it.

Fix Remove ~/.ssh, the agent socket and the gh config from the default path. Make them opt-in (--with-ssh, --with-gh) and prefer a per-session deploy key with a short agent lifetime or a host-side credential broker. Never mount auth.json into an untrusted session.

Critical

Writable config dirs create host persistence

run.sh:171–179, 88–110

What the code does ~/.claude and ~/.config/opencode are mounted read-write. Those directories contain hooks, commands, skills, plugins, and cli.json with absolute plugin paths. run.sh itself parses cli.json to decide which host paths to mount.

Why it matters These are code and config that OpenCode or Claude Code load on the host later. A container session can plant a hook, plugin or command that executes outside the container on the next host run. That turns a container compromise into host code execution without needing a kernel escape. Writable shared state also lets a malicious session tamper with your trusted tools.

Fix Mount config read-only by default. If a session must write config, point it at a separate per-session directory and diff it before merging. Treat ~/.claude and ~/.config/opencode as supply-chain inputs, not scratch space.

High

Shared kernel and default container privileges

run.sh:75; Dockerfile:155

What the code does The container is not a VM. It runs with Docker’s default capability set and default seccomp/AppArmor profiles. There is no --cap-drop=ALL, no --security-opt=no-new-privileges, and no user-namespace remapping. USER agent removes root inside the container but does not change the kernel boundary.

Why it matters A kernel or container-runtime escape is host compromise on Linux; on Docker Desktop it compromises the shared Linux VM that holds every container and your mounts. That is an acceptable trade for trusted workloads and the right trade for a dev image; it is not acceptable as the containment story for untrusted repos or autonomous agents.

Fix Add --cap-drop=ALL, --security-opt=no-new-privileges, a read-only rootfs with explicit tmpfs mounts, and consider userns-remap. For untrusted work, move to gVisor/Kata or a microVM rather than accumulating flags.

High

Secrets passed as environment variables are not hidden from the container

run.sh:219–244; README:171–184

What the code does --env NAME copies the value from the launching process, so the secret does not appear on the shell command line. The README correctly says so. The resolved value is still written into the container config and into the process environment.

Why it matters docker inspect <id> shows it under .Config.Env, and any process in the container can read /proc/<pid>/environ. “Not on the command line” is easy to over-read as “not visible”. --env-file has the same property; it only changes how the launcher reads it.

Fix Use a host-side broker/proxy or short-lived tokens. If a value must be in the environment, accept that it is readable and bound its scope and lifetime. Do not put long-lived personal tokens there.

High

Project-controlled plugins, skills and instructions execute inside the session

repo mount: run.sh:136–139; OpenCode config discovery

What the code does The repo is mounted read-write. OpenCode auto-loads .opencode/plugins/*.ts|js, project config, project skills and AGENTS.md from it. The container also has your mounted credentials and open egress.

Why it matters In an untrusted repo these are attacker-controlled code and prompt input. A project plugin runs with the OpenCode server’s privileges; a project instruction can steer the agent toward the mounted keys. This is the direct exfiltration path: untrusted repo + readable secrets + open network.

Fix Run untrusted repos inside a VM/microVM with no host credentials. If that is not possible, deny project plugin targets at the system policy layer, disable project config/plugin discovery for the session, and mount the repo read-only except a scratch worktree.

High

No resource limits

run.sh:75

What the code does There is no --pids-limit, --memory, --cpus, or ulimit configuration. --init only reaps zombies.

Why it matters A fork bomb, runaway test suite, memory-hungry build or accidental parallel process storm can degrade or lock up the host. Availability is part of the threat model, especially for autonomous runs.

Fix Start with --pids-limit=2048 --memory=8g --cpus=4, plus --ulimit nofile=4096:8192. Tune to the workload; enforce them through the wrapper, not the agent’s goodwill.

Medium

safe.directory '*' disables git’s ownership check everywhere

Dockerfile:136–138

What the code does git config --system --add safe.directory '*' tells git to trust every repository path regardless of ownership.

Why it matters That protection exists because a repository owned by another user can carry config and hooks you did not choose. Blanket trust is broader than the actual need, which is the bind-mounted repo and its git common dir.

Fix Add only the mounted paths, preferably at runtime: git config --global --add safe.directory "$REPO_ROOT" and the worktree common dir. Keep the image’s system config clean.

Medium

No host-trust path for SSH

run.sh:271–279; README:116–117

What the code does ~/.ssh is mounted read-only, so known_hosts cannot be updated from inside the container. A new host must be trusted on the host first.

Why it matters This is operationally awkward and encourages the worst workaround: StrictHostKeyChecking=no or an empty known_hosts, which removes host verification entirely. Security controls that are annoying get disabled.

Fix Pre-seed known_hosts in the image for the hosts you use, or mount a writable per-session copy and use StrictHostKeyChecking=accept-new deliberately. Never disable verification globally.

Medium

Docker-in-container is absent

run.sh mounts (no docker socket)

What the code does The host Docker socket is deliberately not mounted, so agents cannot build images or run containers from inside the session. That is the right default for security.

Why it matters It is a functional gap for repos whose tests build images or compose stacks. The tempting fix — mounting the host socket — is effectively root on the host and would dominate every other finding here.

Fix Do not add the socket. If Docker access is required, use rootless DinD, Sysbox, or a microVM with its own private daemon (sbx). Treat any Docker-capable sandbox as a higher-risk profile.

Medium

Image supply chain is loose

Dockerfile:8, 10, 12, 57–68, 99–106

What the code does Base images (debian:bookworm-slim, node:…-bookworm-slim, ghcr.io/astral-sh/uv:…) are tag-pinned, not digest-pinned. OpenCode is installed by downloading a script with curl from opencode.ai and running it with bash. The gh keyring and apt repositories are fetched at build time. There is no SBOM, provenance attestation, signature, or documented rebuild cadence.

Why it matters A moved tag or compromised install endpoint becomes code in your image. You cannot answer “what exactly is in the image we ran last month?” without a rebuild and a diff.

Fix Pin digests, verify the installer checksum/signature, build with --sbom --provenance, sign with cosign, and schedule rebuilds. Add a smoke test that asserts the security properties you rely on.

Medium

Dockerfile.new is dead and broken

docker/opencode/Dockerfile.new

What the code does It downloads a nonexistent uv-3.13-linux-x86_64.tar.gz into /usr/local/bin/uv, swallows failures with || true and || :, sets an /opt/uv path it never creates, and installs OpenCode from npm — the approach the real Dockerfile intentionally avoids. It also references an undefined ${PYTHON_VERSION} build arg, and sets npm’s prefix and PATH to /home/.opencode/local/bin, which it never creates.

Why it matters Nobody should build it, but its presence invites confusion and supply-chain drift. Broken build files are a classic source of “we thought that was the image”.

Fix Delete it. If it is a sketch, keep it outside the build context or in a branch with a README that says it is not buildable.

Low

UID/GID baked at build time

Dockerfile:16–17, 112–134; Makefile:25–29

What the code does The agent user is created with the build host’s UID/GID. Published multi-arch images force 1000:1000, and run.sh warns on mismatch.

Why it matters Nice for local bind-mount ownership; bad for a portable published image. A mismatch means read/write failures or files owned by the wrong host user.

Fix For portability, run with --user "$(id -u):$(id -g)" against a world-readable toolchain, or use user-namespace remapping. Document the local-build path as the supported one.

Low

Writable rootfs and a full build toolchain

Dockerfile:20–47, 155

What the code does The image keeps a compiler, headers, git, Node, Python and package managers, and the rootfs is writable.

Why it matters That is a larger attack surface than a minimal runtime: more binaries to exploit, more places to persist, more supply-chain entry points. It is also exactly what makes it a good dev image.

Fix Accept it for trusted dev work. For a sandbox profile, layer a read-only rootfs with a tmpfs workspace and a smaller runtime image; or move the toolchain into the VM where it is contained.

Low

Repo mounted at the same absolute path

run.sh:136–139

What the code does The repo is mounted read-write at the same absolute host path, which keeps symlinks and prompt paths truthful. The same mount exposes .git/hooks, .git/config, package scripts, the Makefile and CI config.

Why it matters That fidelity is genuinely useful. It also means the agent can modify anything that executes when you later run the repo on the host. Treat the working tree as code execution, not just data.

Fix Review diffs before running repo scripts; use a clone/worktree for untrusted work; mount .git read-only when the task does not need commits. Do not let an agent-owned worktree become your trusted checkout.

No findings at this severity.

04Docker Sandboxes · sbx

The boundary Docker actually recommends

Docker Sandboxes is a separate product from the Docker engine: a CLI (sbx) that runs a coding agent inside a microVM, with a host-side proxy owning both the network policy and the credentials. It is the closest turnkey answer to “run OpenCode on a repo I do not trust”.

What sbx gives you

Recommended boundary
  • MicroVM per sandbox: its own kernel, filesystem and process tree. A kernel escape lands in the guest, not the host.
  • Private Docker daemon inside the VM: agents can build and run containers without the host socket. This is the safe answer to Docker-in-Docker.
  • Workspace modes: a direct read-write mount, or --clone — the host repo is mounted read-only at /run/sandbox/source and the agent works on a private in-VM clone.
  • Deny-by-default egress: outbound TCP goes through a host-side proxy with a per-sandbox network policy. LAN, metadata and host services are blocked unless allowed.
  • Host-side credential injection: sbx secret set stores the secret on the host; the proxy adds the auth header. The VM never holds the real value.
  • OpenCode is a built-in agent: sbx run opencode ~/project.

Credentials and providers

Built in

Provider secrets are supported for Anthropic, OpenAI, OpenRouter, Google, xAI, Groq and AWS. GitHub Copilot works through a GitHub credential. OpenCode Zen needs a custom secret for opencode.ai plus an explicit network rule:

opencode zen inside sbxbash
sbx secret set custom opencode.ai --value "$OPENCODE_ZEN_KEY"
sbx policy allow network opencode.ai:443
sbx run opencode --clone ~/project

Exact flag names can move while sbx is 0.x; check sbx secret --help and sbx policy --help on the installed version.

Requirements and limits, stated plainly
  • Platforms: local sandboxes need macOS 14+ on Apple silicon, Windows 11 with the Windows Hypervisor Platform, or Ubuntu 24.04+ with KVM and your user in the kvm group. VMs/VDI need nested virtualisation.
  • Maturity: the runtime is closed source and 0.x. sbx login is required. Kits are marked experimental. Expect CLI and policy syntax to move.
  • Your dotfiles do not come along: user-level agent config is not mounted by default — only project config and the shared skills store. This repo’s ~/.claude / ~/.config/opencode setup needs importing or adapting. That is a portability gap, not a leak.
  • The built-in OpenCode template is minimal. The current toolchain (Node, uv/Python, gh, git-lfs) needs a custom kit/template if the repo depends on it.
  • Direct mode is still your working tree. It lets the agent edit files and .git/hooks. Use --clone for untrusted repos even though the VM boundary holds.
  • Cost: local sandboxes are free; cloud sandboxes are paid.

05Wider landscape

Every credible option, and what each is for

A Dockerfile, devcontainer or compose file is packaging. The runtime underneath decides what a bad command can reach. Pick the boundary first, then the tooling that fits it.

Docker Sandboxes (sbx)

Best default for untrusted

A microVM per sandbox with its own kernel and private Docker daemon, a host-side credential proxy, and deny-by-default egress. OpenCode is a built-in agent.

Use when the repo or agent is untrusted and you want a turnkey laptop boundary. Caveats: 0.x, limited platforms, dotfiles and toolchain need porting, clone mode for untrusted work.

Hardened container + egress proxy

Cheapest upgrade

--cap-drop=ALL, --security-opt=no-new-privileges, --pids-limit, --memory, --cpus, read-only config, no SSH by default, plus a proxy sidecar or host firewall allowlist.

Use when repos are trusted and you want to reduce accidental damage and casual exfiltration. Still a shared kernel, so it is not equivalent to a VM.

gVisor / Kata / Sysbox

Stronger runtime, same workflow

docker run --runtime=runsc (gVisor) intercepts syscalls in user space. Kata gives a lightweight VM per pod/container. Sysbox is useful when the agent needs Docker-in-Docker without a privileged host socket.

Use when you cannot rewrite the app but need more than namespaces. More ops work than sbx, and still not as clean for laptop use.

Dev Containers

Packaging + editor integration

Not isolation by itself. Anthropic’s reference devcontainer shows the useful pattern: default-deny iptables/ipset firewall with NET_ADMIN + NET_RAW, allowlisting api.anthropic.com, GitHub ranges, npm registry and similar.

Use when you want VS Code/Cursor integration and a reproducible definition. Point a devcontainer at this Dockerfile and keep the firewall; the runtime still decides the boundary.

microsandbox (msb)

Open-source microVMs

libkrun microVMs running OCI images, with host-side secret injection, network allowlists, snapshot/fork and cross-platform support. Self-hosted, no closed runtime.

Use when you want sbx-like isolation without the closed-source runtime or platform lock-in. Beta/0.x with a smaller ecosystem; expect to operate it yourself.

container-use (Dagger)

Not a full boundary

An MCP server that gives an agent a fresh container and a git branch. The agent process stays on the host; only tool-driven work runs in the container.

Use when you want parallel agents and isolated worktrees with reviewable branches. It is not a containment boundary for the agent itself — keep that caveat in the design.

Cloud sandboxes

No host at all

E2B, Daytona, Vercel Sandbox, Modal, Cloudflare Sandbox: ephemeral microVMs, per-sandbox egress policy, credential brokering, API-driven lifecycle.

Use when runs are unattended, CI-driven or embedded in a product. Less ideal for interactive local dotfiles: latency, data movement and per-run cost.

OS-level wrappers

Process containment

bubblewrap, nsjail, firejail, macOS Seatbelt/sandbox-exec, and Anthropic’s @anthropic-ai/sandbox-runtime. Useful network default-deny and filesystem scoping without a full VM.

Use when you want to contain one process or command. Weaker than a VM, often platform-specific, and easy to misconfigure into a false sense of security.

OpenCode Manager sandboxing

Product-specific

If you use that product, it can run shell tool commands in a per-session microVM on Linux/KVM.

Use when you already run OpenCode Manager on Linux with KVM. It is not a general answer to “how do I run this Docker image safely”.

Anti-patterns

Do not
  • Mounting the host Docker socket.
  • --privileged Docker-in-Docker.
  • Running the agent as root on the host or in a shared container.
  • Mounting all of $HOME.
  • Relying on --auto or permission prompts as a security boundary.
  • Treating read-only as “cannot be exfiltrated”.
06OpenCode-native controls

Permissions, policies, plugins, hooks

OpenCode V2 has a real policy surface. It is useful, and it is not a sandbox. The distinction that matters: a boundary changes what the process can physically reach; policy changes what the tool layer will allow; guardrails inspect and rewrite calls in-process; approval puts a human in the loop.

Boundary vs policy vs guardrail

A microVM/container/proxy is the boundary. A policies entry is a hard deny evaluated after approvals. A permissions entry is an ordered allow/ask/deny rule for tools. A plugin hook runs inside the OpenCode server, so it can inspect, block and rewrite — but it cannot protect a secret that is readable in the container, and a malicious plugin has the server’s privileges. A human approval is a decision, not a control that survives an unattended run.

Permissions

V2 uses permissions (plural), not the V1 permission. Rules are ordered {action, resource, effect} objects and last match wins. Actions include read, edit, glob, grep, shell, subagent, skill, question, webfetch, websearch, external_directory, MCP tools, and execute.

The defaults are permissive: * allow, with *.env and *.env.* set to ask, and external_directory allowed by default. The shell action runs with the host user’s filesystem, process and network authority; directory inference from a command string is best-effort, not a security parser. Prefer a narrow allowlist to clever pattern matching.

~/.config/opencode/opencode.jsonc — user permissionsjsonc
{
  "permissions": [
    // Baseline: ask for every shell command ...
    { "action": "shell", "resource": "*", "effect": "ask" },
    // ... except the read-only git commands you run constantly.
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    // Never push from inside the session.
    { "action": "shell", "resource": "git push *", "effect": "deny" },
    // V2 allows external_directory by default; restore the older safety.
    { "action": "external_directory", "resource": "*", "effect": "ask" },
    // Deny wins if it appears after the default ask rule.
    { "action": "read", "resource": "*.env", "effect": "deny" },
    { "action": "read", "resource": "*.env.*", "effect": "deny" }
  ]
}

Per-agent rules append rather than replace project/global rules, so an agent cannot widen its own policy by declaring a friendlier list. A saved “always allow” approval becomes a durable, project-scoped allow rule; it cannot override a deny. Review saved approvals periodically — they are easy to accumulate and hard to notice.

Pattern matching is not command parsing. A prefix allow such as git status * can also match a chained command, so keep allow rules exact and short. Shell permissions reduce mistakes; they are not a containment boundary.

Policies

policies are binary hard-deny (allow/deny), never prompt, and are evaluated after approvals. Actions are provider.use, tool.use and integration.use; resources look like shell:git push *, edit:*.env, webfetch:*, mcp:github, plugin:opencode-acme.

Precedence runs managed/system/Console above global and project config: a repo cannot re-enable a provider denied in /etc/opencode. Bake a policy file into the image at /etc/opencode/opencode.jsonc (system-wide) and mount user/project config read-only. Policy and config plugins cannot be disabled from the plugins list — that is the point of putting them at the system layer.

/etc/opencode/opencode.jsonc — baked into the imagejsonc
{
  "policies": [
    // No browsing unless the task genuinely needs it.
    { "action": "tool.use", "resource": "webfetch:*",  "effect": "deny" },
    { "action": "tool.use", "resource": "websearch:*", "effect": "deny" },

    // Destructive / secret-bearing operations are hard denies.
    { "action": "tool.use", "resource": "shell:sudo *", "effect": "deny" },
    { "action": "tool.use", "resource": "edit:*.env",   "effect": "deny" },

    // Deny the providers you do not use; allow documents the intended one.
    // Deny is what enforces. Add a deny for every unused provider.
    { "action": "provider.use", "resource": "openai",    "effect": "deny" },
    { "action": "provider.use", "resource": "anthropic", "effect": "deny" },
    { "action": "provider.use", "resource": "openrouter", "effect": "allow" },

    // Project plugins are code. Block their use in untrusted repos.
    { "action": "integration.use", "resource": "plugin:*", "effect": "deny" }
  ]
}

This is the only layer a repository cannot override. In a shared-kernel container it still cannot stop a process from reading mounted files directly; pair it with the boundary work in sections 4, 5 and 7. Policy resources are matched, not parsed: shell:sudo * will not catch every equivalent command. Treat policy as a strong guardrail for known-bad shapes, not proof of safety.

Plugins and hooks

V2 plugins are defined with Plugin.define({ id, async setup(ctx) { … } }). The hooks below run in-process. Each can inspect or mutate; a thrown error blocks the operation where the hook contract allows it. An explicit configured deny is final and does not invoke the permission hook.

ctx.permission.hook("evaluate") — allow / ask / deny decisions

Runs for allow/ask decisions. It can escalate to ask or deny, relax to allow, and set a message shown to the user. It does not run for an explicit configured deny, because that decision is already final. Use it for context-sensitive rules the static pattern language cannot express.

ctx.tool.hook("execute.before") / ("execute.after")

execute.before sees the tool and input before execution; mutate the input to narrow it or throw to block. execute.after sees status, content and error; use it to redact secrets from results or append an audit warning. Do not rely on execute.before alone as the deny contract where a permission rule is available.

ctx.shell.hook("create.before") — rewrite a command

Runs before a shell command is executed. It can rewrite command, cwd, timeout and env. This is the right place to wrap a command, log it, or add a defensive environment variable. It is not a shell parser; a rewrite can be defeated by a sufficiently creative command, so keep the allowlist rules at the permission layer too.

ctx.session.hook("prompt") — redact before admission

Receives the prompt text and attached files before the prompt is admitted. Redact secrets pasted by a user, append policy text, or remove files that should not enter the model context. This protects the model call, not the filesystem: the agent can still read the file through the read tool if permissions allow it.

ctx.session.hook("context") — shape the model call

Runs before a model call and can modify system instructions, messages, tools and options. Use it to inject policy reminders, drop a dangerous tool for a specific agent, or add context. Dropping a tool here reduces what the model is offered; it does not remove the tool from the server or stop a shell command from doing the same thing.

ctx.session.hook("http.request") — provider request / headers

Can modify native provider requests and headers. Useful for routing through a proxy, adding audit headers, or changing a base URL. It is not a way to hide a key that is already in the container: the plugin runs in the same process and the key is still readable. Use a host-side broker for that.

Transforms: tools, MCP, skills, agents, plugin list

ctx.tool.transform removes or updates tools; ctx.mcp.transform disables MCP servers; ctx.skill.transform filters skills; ctx.agent.transform changes agents; ctx.plugin.list exposes the loaded plugins. Transforms are configuration surgery, not a boundary — a disabled tool can often be replaced by a shell command.

~/.config/opencode/plugins/sandbox-guard.ts — block .env reads, audit shellts
import { appendFile } from "node:fs/promises"
import { Plugin } from "@opencode/plugin"

const AUDIT = process.env.AGENT_AUDIT_LOG ?? "/var/log/opencode/audit.jsonl"
const SECRET = /(^|\/)\.env(\.|$)/

export default Plugin.define({
  id: "sandbox-guard",
  async setup(ctx) {
    // 1. Refuse reads of .env files. A configured deny is already final.
    ctx.permission.hook("evaluate", async (event) => {
      if (event.action !== "read") return
      if ((event.resources ?? []).some((r) => SECRET.test(r))) {
        return { effect: "deny", message: "Blocked by sandbox-guard: .env reads" }
      }
    })

    // 2. Audit every shell command before it runs.
    ctx.shell.hook("create.before", async (event) => {
      await appendFile(AUDIT, JSON.stringify({
        ts: new Date().toISOString(),
        kind: "shell",
        agent: event.agent ?? null,
        cwd: event.cwd,
        command: event.command,
      }) + "\n")
    })

    // 3. Record failed tool calls for review.
    ctx.tool.hook("execute.after", async (event) => {
      if (event.status !== "error") return
      await appendFile(AUDIT, JSON.stringify({
        ts: new Date().toISOString(),
        kind: "tool-error",
        tool: event.tool,
        error: event.error,
      }) + "\n")
    })
  },
})

Write the audit log to a dedicated host state directory or volume owned by the agent UID, never the repo: -v "$HOME/.local/state/opencode/audit:/var/log/opencode". Even then, a compromised agent runs with the server’s privileges and can tamper with any file it can write; for tamper-evident audit, ship the log off the machine as it is written.

Controlling plugins

Supply chain

Use the plugins list to keep everything except one package: "plugins": ["*", "-some.plugin"]. Inspect what is loaded with opencode plugin list. Block a specific integration at the policy layer with an integration.use deny for plugin:<target>.

Project .opencode/plugins auto-load. That is convenient for a trusted repo and unacceptable for an untrusted one. Deny/disable project plugin targets at the system policy layer, or keep the repo inside a VM.

What hooks cannot do

Limits

They cannot make a mounted private key unreadable, stop a process from opening a socket, or contain a kernel exploit. A malicious plugin can remove the guard, read the same files, or rewrite the log. Hooks are for discipline, audit and mistake-prevention inside a boundary you already trust.

A hook is not a sandbox: OpenCode runs shell commands with the same OS authority as the server. If the agent can run curl, a hook must catch it; if the hook is bypassed, nothing else will.

Built-in features worth using

--auto

Only inside a real boundary. It removes the human approval step; it does not add containment.

external_directory

Set ask or deny. V2 defaults to allow, so this is an explicit downgrade from V1 behaviour.

.env read rules

Deny *.env and *.env.* after the defaults. Combine with not mounting secret files in the first place.

provider.use

Deny providers you do not use. A provider that has no credential is also unavailable, but do not rely on that alone.

MCP tool permissions

Per-tool rules, not just per-server. A GitHub MCP server that can merge PRs is a different risk from one that only reads issues.

skill and subagent

Deny skills by ID and agents by name. This is how you reproduce Claude’s “disabled skills” behaviour in OpenCode.

webfetch / websearch

Deny unless the task needs the open web. If it does, route through a proxy with an allowlist rather than the container’s default route.

question

Ask-before-acting is useful for ambiguous operations, but it is a UX control. It cannot protect an unattended run.

TUI approval flow

Good for interactive work; saved approvals become durable project-scoped allow rules. Review them and prefer narrow resources.

cli.json plugin entries

The statusline/local TUI plugin path. run.sh mounts those host paths read-only, which is the right default: the plugin runs but cannot rewrite itself.

V1 vs V2: the names changed

OpenCode V2 hooks differ from V1: permission → permissions, bash → shell, task → subagent. V1 plugins use server(); V2 uses setup(). This repo’s docs/opencode-port.md documents the full V1→V2 mapping, including agent frontmatter, commands and the Claude hook bridge.

07Credentials

Give the session a capability, not your identity

The core principle is not “hide the key better”. It is: do not put your identity in the sandbox. Give it a scoped, short-lived capability that is useful for this task and worthless everywhere else.

1. Host-side broker or proxy

Best

The real secret never enters the container/VM. Per-service and per-sandbox scope, a TTL, audit logs and an egress allowlist all live on the host. sbx secret set is the turnkey version; a host LiteLLM/OpenRouter/custom proxy or MCP gateway is the DIY version.

For provider APIs a proxy can inject auth headers. For git/gh, use a credential helper or a short-lived token: an HTTPS CONNECT proxy cannot inject headers into TLS without terminating it.

2. Short-lived, scoped tokens

Good

Even if the agent sees them, blast radius and time are bounded: GitHub App installation token or fine-grained PAT, OIDC→STS, ssh-add -t 1h with a dedicated deploy key, a per-session read-only database user.

Prefer per-repo, per-environment and read-only. A token that expires in an hour is a very different asset from a personal PAT that lives for a year.

3. Launch-time resolution into files/env

Acceptable

1Password op run/op read, SOPS+age, the OS keychain, KeePassXC keepassxc-cli show, mounted /run/secrets/* files. Keeps secrets out of the image and out of git.

1Password is the turnkey op run equivalent; KeePassXC has no exec wrapper, so you write the wrapper yourself and non-interactive unlock is awkward. Either way the agent can read the value. Do not pretend this is isolation; it is hygiene and lifecycle management. Use it when the workload is trusted.

4. Never

Avoid

Dockerfile ARG/ENV, committed .env, -e KEY=value, --env-file with long-lived secrets, mounting ~/.ssh, ~/.config/gh, auth.json, a host gitconfig with credential helpers/tokens, or a personal long-lived PAT.

These are not different degrees of the same thing. They are identity handovers with no expiry and no scope.

Approve once, use for the whole job

Approving every token refresh makes an unattended job impossible. The fix is not to copy a long-lived PAT into the container and hope the job finishes before the token leaks. It is a lease: the host broker records exactly what a human approved, then mints and refreshes credentials against that approval without asking again.

A lease lives on the host, not in the container. It is scoped to the session or sandbox ID, the service (GitHub, Anthropic, AWS), the resource (one repo, org, role or bucket), the allowed actions (read, write, push) and a TTL. It has an ID and an audit trail. The container holds either a short-lived token or a sentinel/handle that only the broker can redeem for the real credential.

  1. Approve capability

    A human approves one service, resource, action set and expiry. The secret value stays in the vault; the approval names a capability, not a copy of the key.

  2. Issue lease

    The broker records the lease ID, scope and TTL, and gives the container a short-lived token or a sentinel. The lease is the thing that is reused, not the secret.

  3. Use / refresh token

    The container calls the service through the broker. The broker injects or refreshes the credential until the lease expires, and logs each use.

  4. Revoke or expire

    A human can revoke immediately; otherwise the TTL ends it. The long-lived root secret is untouched and does not need rotating because a session ended.

What the container actually gets

Scoped
  • GitHub: a GitHub App installation token, about one hour, for one repo or org and only the scopes the task needs. The broker can mint a fresh one while the lease holds.
  • Cloud: OIDC→STS credentials for one role, refreshed by the broker before expiry.
  • Providers: a proxy base URL and a virtual key, or a sentinel. The real provider key never enters the container.
  • Not: a personal PAT, a static access key, or a root credential dressed up as a session token.

Lease reuse, not secret caching

The distinction

“Reuse the approval” means the broker reuses the lease to mint or refresh short-lived tokens. It does not mean caching the long-lived PAT in the container for the duration of the job.

If the only credential available is a long-lived PAT, caching it for the job is a pragmatic fallback, but state it plainly: one leak is the whole token until someone revokes it, and the container can read it the entire time. A lease is strictly better because the exposed artifact expires.

Approval and visibility

Human in the loop, once

Offer Allow once, Allow for this session, Allow for 8h and Deny. Show the service, resource, actions and expiry in the prompt; never ask the human to paste the secret.

Prefer a visible lease indicator — service, scope, TTL and last used — over a silent cache. A lease should be revocable from the same place it was approved, with the revocation taking effect on the next request.

What the vault is (and is not)

Not a broker

1Password, KeePassXC and Secret Service supply the root secret to the broker after unlock. They do not implement approval, leases, refresh or revocation.

Secret Service is host-wide and not approval-scoped; KeePassXC’s SSH agent exposes every key in the open database. The vault stays on the host, and the container talks to the broker, never to the vault. “Approve once” is a broker/lease feature, not a vault feature.

Wiring it into OpenCode

  • Host HTTP proxy or local broker: the container reaches one address; the broker holds the root secret and enforces the lease.
  • ctx.session.hook("http.request"): can add headers or point provider calls at the broker. It runs in-process, so it should carry a lease token, never the root secret.
  • Credential helper or wrapper: for git and gh, fetch or refresh the lease token at call time and hand it to the helper, not to the shell history.
  • Never put the lease root, broker admin key or long-lived PAT in the repo, project config or an agent-readable file. Project config is attacker-writable.
Long-running jobs

A GitHub Actions-style job can outlive a one-hour installation token; that is not a reason to export a PAT. While the lease is active, the broker refreshes the installation token in the background. If the session gets a 401, it should ask the broker for a refresh, not re-prompt the human. For SSH there is no equivalent: a one-hour ssh-agent key is a hard limit. Extend it by re-adding the same key under the lease if policy allows, rather than falling back to a permanent key.

Recommended

Acceptable

Fetch one attribute with keepassxc-cli show -q -s -a Password into a mode-0600 file, mount it read-only at /run/secrets/<name>, and delete it after start. Or, when the DB is already unlocked, use Secret Service plus secret-tool lookup.

This keeps the value out of the image, git, argv and shell history. Once injected, the agent can still read it.

Avoid

Mounting the .kdbx, using the personal vault, relying on KeePassXC’s global SSH agent, or putting the master password in argv or shell history. There is no op run-style exec wrapper, so do not pretend a one-liner gives you brokering.

wrapper: fetch named entries at launch, never mount the DBbash
#!/usr/bin/env bash
set -euo pipefail
umask 077
DB="${KEEPASS_DB:-$HOME/.config/keepass/agent.kdbx}"
get() { keepassxc-cli show -q -s -a Password "$DB" "$1"; }
ANTHROPIC_API_KEY="$(get 'agent/anthropic')" \
  exec docker run --rm --init --env ANTHROPIC_API_KEY ...

--env is still visible in docker inspect and /proc/<pid>/environ, so a mode-0600 file mount or a host broker is better. keepassxc-cli show can also fetch custom attributes with -a and TOTP with -t; -s prints a protected attribute in clear text. There is no service-account or token equivalent, and non-interactive unlock is awkward. It is a vault, not a broker: no per-request injection, TTL or audit. Secret Service can serve values to secret-tool while the DB is unlocked, but it is host-wide and not approval-scoped: it is a backend for a broker, not a substitute for one. KeePassXC’s SSH agent exposes every SSH key in the open database; for containers prefer a fresh session ssh-agent loaded with one deploy key (ssh-add -t 1h).

What docker inspect actually shows

--env NAME avoids the shell command line, but the resolved value is stored in the container config. Anyone who can run docker inspect on the host — or read /proc/<pid>/environ inside the container — can see it.

verify it yourselfbash
docker inspect --format '{{json .Config.Env}}' <container> | jq .
# ["ANTHROPIC_API_KEY=sk-ant-...", "GH_TOKEN=ghp_...", ...]

--env-file is the same story: the launcher reads the file, Docker stores the values. Process substitution or 1Password avoids writing a file to disk, but it does not hide the value from the container. The only fixes are a broker, a short TTL, or not giving the session the credential.

Honest DIY proxy sketch

A plain HTTP CONNECT proxy can allowlist destinations, but it cannot inject provider auth headers into TLS unless it terminates TLS with a CA the container trusts. That is a real MITM appliance, not a one-liner. For provider APIs, prefer a provider-aware proxy/baseURL that speaks the API and adds auth itself (LiteLLM, OpenRouter, a custom gateway). For git/gh, inject at the credential-helper layer instead. Do not deploy a “proxy” that only logs the CONNECT target and call it credential brokering.

08Recommendation

What to do, in order

The right answer depends on one question more than any other: do you trust the repo and the agent’s instructions? Everything else is tuning.

Decision helper

Four questions. The recommendation is a starting point, not an oracle; the reasoning is shown so you can disagree with it.

Recommended path

Harden the current Docker image

The repo and instructions are trusted, so a shared-kernel container is a reasonable developer environment. Spend the effort on capability drops, resource limits, read-only config and an egress proxy rather than on a VM you do not need.

Also consider / next step
  • sbx if the repo or agent trust changes
  • gVisor (--runtime=runsc) if you want a stronger kernel boundary without leaving Docker
Now
trusted repos

Keep the image, remove the sharp edges

This is still a developer environment, but make the default profile the safe one. The goal is to stop accidental damage and casual exfiltration, not to contain a determined attacker.

  • Add --cap-drop=ALL, --security-opt=no-new-privileges, --pids-limit=2048, --memory=8g, --cpus=4.
  • Make ~/.claude and ~/.config/opencode read-only by default; provide a per-session writable overlay if a task needs it.
  • Remove ~/.ssh and ~/.config/gh from the default path. Make them opt-in with --with-ssh / --with-gh / --unsafe.
  • Stop passing long-lived secrets with --env. Use a broker, a short-lived token, or 1Password at launch.
  • Where a broker exists, use a lease: a scoped capability with a TTL, a visible lease indicator and immediate revocation. Keep the root secret on the host; never cache a long-lived PAT in the container.
  • Remove host.docker.internal unless a specific host service is required; gate --network=host behind the unsafe flag.
  • Scope safe.directory to the mounted repo and its git common dir.
  • Delete Dockerfile.new.
hardened baseline for the current wrapperbash
CONFIG_DIR="${XDG_CONFIG_HOME:-$HOME/.config}/opencode"

docker run --rm --init \
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --pids-limit=2048 --memory=8g --cpus=4 \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=2g \
  --tmpfs /home/agent/.cache:rw,size=1g \
  --network opencode-egress \
  -v "$REPO_ROOT:$REPO_ROOT" -w "$REPO_ROOT" \
  -v "$CONFIG_DIR:/home/agent/.config/opencode:ro" \
  opencode-dev:local

Create opencode-egress as an --internal network and attach a filtering proxy to both it and the outside; a plain user-defined bridge still routes to the internet. --read-only needs tmpfs or writable mounts for anything OpenCode writes — add those deliberately, not by dropping the flag.

Next
untrusted

Move the boundary outside the agent

Use sbx on a supported host, or microsandbox where you want an open-source runtime. Keep the current image as the trusted-repo environment; do not try to make it contain an adversary by adding flags.

sbx, minimal OpenCode flowbash
sbx login
sbx secret set anthropic
sbx secret set github --command 'gh auth token'
sbx policy allow network api.anthropic.com:443
sbx policy allow network github.com:443
sbx run opencode --clone ~/dev/project
  • Use --clone for untrusted repos: the host tree is mounted read-only and the agent works on a private clone.
  • Keep the default deny on egress and add only the hosts the task needs; do not reuse a broad host-network preset.
  • Port the current Dockerfile’s toolchain (Node, uv/Python, gh, git-lfs) into an sbx kit/template if the repo needs it. The built-in OpenCode template is minimal.
  • Import only the skills and project config the session needs. User-level config is not mounted by default.
  • For an open-source alternative, evaluate microsandbox on Linux/KVM; expect to operate more of it yourself.
Then
team / CI

Make it repeatable and observable

  • Use a cloud sandbox (E2B, Daytona, Vercel Sandbox, Modal, Cloudflare Sandbox) for unattended runs, or a hardened container with an egress proxy on your own runners.
  • No host credentials in the runner. Mint per-run tokens from the CI identity and let them expire.
  • For long-running jobs, implement a lease broker — or use sbx’s proxy plus sbx secret with a GitHub App token refresh sidecar — rather than exporting a PAT. Handle a 401 by refreshing the lease, not by re-prompting a human.
  • Ship audit logs off the machine as they are written; a log the agent can edit is not an audit trail.
  • Pin the image digest per pipeline and record which agent/config version ran.
  • Keep a smoke test that asserts: no host Docker socket, no ~/.ssh, no secrets in docker inspect, expected network allowlist.
Hygiene
image

Make the image explainable

  • Digest-pin debian, node and uv base images.
  • Verify the OpenCode installer checksum or signature instead of trusting a downloaded script.
  • Build with docker buildx build --sbom --provenance; sign with cosign.
  • Document the rebuild cadence and who owns it. A stale dev image is a quiet supply-chain risk.
  • Add a smoke test for the security properties, not just the toolchain versions.

OpenCode config baseline

Bake the system policy into the image, keep the user permissions narrow, and ship one small guard plugin.

{
  "policies": [
    { "action": "tool.use", "resource": "webfetch:*", "effect": "deny" },
    { "action": "tool.use", "resource": "websearch:*", "effect": "deny" },
    { "action": "tool.use", "resource": "shell:sudo *", "effect": "deny" },
    { "action": "tool.use", "resource": "edit:*.env", "effect": "deny" },
    { "action": "integration.use", "resource": "plugin:*", "effect": "deny" },
    { "action": "provider.use", "resource": "openai", "effect": "deny" }
  ]
}

A repo cannot override this file. Add provider denies for every provider you do not use; deny project plugin targets when the repo is not trusted.

Order matters: the last match wins. Review saved “always” approvals; a saved allow cannot override a deny.

plugin skeleton — audit shell, block .envts
import { appendFile } from "node:fs/promises"
import { Plugin } from "@opencode/plugin"

const AUDIT = "/var/log/opencode/audit.jsonl"

export default Plugin.define({
  id: "sandbox-guard",
  async setup(ctx) {
    ctx.permission.hook("evaluate", async (e) => {
      if (e.action === "read" && (e.resources ?? []).some((r) => /(^|\/)\.env(\.|$)/.test(r)))
        return { effect: "deny", message: "No .env reads in this session" }
    })
    ctx.shell.hook("create.before", async (e) => {
      await appendFile(AUDIT, JSON.stringify({ ts: Date.now(), cwd: e.cwd, command: e.command }) + "\n")
    })
  },
})
What “secure” means here

No local shared-kernel container protects a truly malicious agent from a kernel exploit. If that is in your threat model — and for untrusted repos or unattended autonomy it should be — use a microVM or a cloud sandbox. Hooks, permissions, read-only mounts and approval prompts reduce mistakes and raise the cost of casual exfiltration. They do not change what the kernel allows.
