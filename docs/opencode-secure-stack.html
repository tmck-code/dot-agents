Secure OpenCode stack: implementation plan

Trusted repos, Docker, local-only. Harden the existing opencode-dev image, put the agent on an internal network, and make a local proxy, lease broker and model reverse proxy the only way out. No paid vault, hosted sandbox or cloud broker.

27 October 2026 tmck-code/dot-agents OpenCode · Docker Engine / Desktop 4 capabilities · 5 diagrams
Verdict

Keep Docker for trusted repos. Put the boundary around the agent, not inside the prompt.

The image is a development environment; the network and the broker are the security boundary. A shared-kernel container with dropped capabilities, no host credentials and no direct route to the internet is a meaningful blast-radius control for code you already trust. It is not a microVM, and the plan does not pretend otherwise.

Safe defaults stay on: one opencode-dev target, an internal-only agent network, root secrets on the host, and an explicit --unsafe escape hatch for debugging.

02Scope & assumptions

What this plan does — and deliberately does not

The target is the developer workflow you already have: the repo at the same absolute path, the same toolchain, worktrees and OpenCode config. The change is not a new sandbox product; it is a local security stack wrapped around one hardened image.

Trusted repos

Assumption

This is a blast-radius and credential-scoping control for repos and instructions you already trust. It is not a claim of kernel-level isolation, and not a place to run hostile code.

Local-only and free

Constraint

SOPS + age (or a dedicated KeePassXC agent DB), Squid, LiteLLM and a small FastAPI lease broker. Everything runs on the host or in local containers. No hosted secret manager, paid sandbox or cloud broker.

One image target

Decision

Keep a single opencode-dev target. Agents need the compiler, Node, uv/Python, git, gh and git-lfs; a runtime-only split would double the build matrix and diverge from real use.

A Baseline decisions that shape the rest of the plan
Image target
One opencode-dev target, hardened at build time (non-root, digest pins, checksum-verified installer, read-only system config, no embedded secrets).
Runtime posture
Non-root, --cap-drop=ALL, no-new-privileges, PID/memory/CPU limits, read-only host config, no SSH or gh mounts by default, no host gateway and no host Docker socket.
Read-only rootfs
Opt-in via --read-only, with tmpfs and named writable volumes, until the toolchain and OpenCode caches are verified.
Project plugins
Allowed for trusted repos when system policy approves them, and their tool calls are audited. Untrusted work can deny integration.use without changing the image.
Escape hatch
--unsafe restores legacy mounts, host gateway and token forwarding for debugging, and prints a warning listing exactly what it exposes. Safe defaults never silently degrade.
Isolation limit
The container shares the host kernel. That is acceptable under the trusted-repo assumption; a microVM is the right tool if that assumption ever changes.
B Goals carried over from the audit
  • Preserve repo-at-same-path and linked-worktree behaviour.
  • Make the container a meaningful network boundary: internal-only agent network, proxy-only egress.
  • Keep root secrets on the host and give the agent scoped, expiring capabilities.
  • Refresh GitHub App installation tokens while a lease stays active, so long jobs do not need a human every hour.
  • Make OpenCode policy independent of the repository and outrank project config.
  • Keep every phase shippable and keep --unsafe available for rollback.
C Non-goals and honest limits
  • No defence against a malicious agent that exploits the host kernel. This is container isolation, not a microVM.
  • No paid or hosted secret manager, sandbox or cloud broker.
  • No TLS interception by default: no proxy CA, no private MITM key in the agent.
  • No replacement of the existing audit/options SPA; this page is the implementation companion.
  • No port of the Python Claude hooks in this change; the OpenCode plugin hooks are native.
  • No cloud-provider credential leasing beyond the broker interface in phase 3.
The trust line

If the repository, its AGENTS.md, its dependencies or the model output are untrusted, stop. Run the work in a microVM or an ephemeral cloud sandbox instead. This stack is for trusted code with an over-broad agent, not for hostile code.

03Target architecture

One agent network, one egress door

The agent container sits on an internal Docker network with no default route. A small stack is dual-homed: it can reach the internet through an allowlist, while the agent can only reach the stack. Root secrets never enter the agent at all.

Host

Outside the boundary
  • Secret store: SOPS + age, or a dedicated KeePassXC agent database.
  • Lease CLI: approve, list and revoke capabilities; host-only admin listener.
  • Compose stack: Squid, lease broker, LiteLLM, optional read-only mounts.
  • Docker Engine / Desktop with the agent on an internal network.

Agent

Inside the boundary
  • OpenCode plus the normal toolchain, as a non-root agent user.
  • Only the opencode-agent route; no default bridge, no host gateway.
  • Lease token and short-lived installation token — never a root key.
  • Read-only system policy at /etc/opencode/opencode.jsonc.

Network matrix

The agent's HTTP_PROXY / HTTPS_PROXY values are a convenience for well-behaved tools. The internal network is what enforces the route when a tool ignores them.

Root secrets never cross the line

The provider root key stays in LiteLLM. The GitHub App private key stays on the host. The SOPS age key or KeePassXC database never mounts into the agent. The agent receives a lease token and a short-lived credential; nothing else.

04Components

Seven pieces, each with one job

The stack is intentionally boring: a proxy that only forwards allowlisted destinations, a broker that only mints scoped credentials, a model proxy that owns provider keys, and an image/launcher that removes ambient authority. OpenCode policy and plugins are the inner guardrails, not the boundary.

01 Egress proxy (Squid) Hard boundary
default denydomain allowlistno TLS MITMlogging

Default-deny forward proxy with an explicit allowlist for the selected model provider, GitHub, npm, PyPI and whatever else the project actually needs. It sees CONNECT host:443 only; it does not terminate TLS, does not install a CA in the agent, and cannot inject headers.

  • Only the proxy is exposed to the agent; it is dual-homed onto the egress bridge for the far side.
  • Logs allowed and denied destinations with timestamp, session/lease where available, host and result — never bodies or Authorization values.
  • Service-specific auth is handled by LiteLLM or the broker, not by the forward proxy.
  • Cloud metadata and link-local addresses are denied explicitly.
02 Lease broker (FastAPI + SQLite) Hard boundary
approveleaserefreshrevoke

A small FastAPI service with SQLite stores a lease ID bound to a session, service, resource, allowed actions, creation time, expiry and status. The human approves a capability, not a secret. The broker mints GitHub App installation tokens scoped to the lease's repository and permissions, and refreshes them while the lease is active.

  • Host-only admin listener; a separate agent-facing token endpoint. Admin is never exposed on the internal network.
  • App JWT signed with a host-held private key; the agent never sees the key or a long-lived PAT.
  • Revocation returns 403 immediately for new requests; an already-issued installation token dies at its GitHub expiry.
  • Runs non-root with a read-only rootfs and a dedicated state volume; token issuance is logged without the token value.
03 LiteLLM provider proxy Hard boundary
root keys herevirtual keysbudgetduration

Provider root keys live only in LiteLLM. OpenCode points its provider base URLs at http://litellm:4000 and authenticates with a per-lease virtual key issued by the broker. The virtual key carries a model allowlist, budget and duration, and is rejected when the lease expires or is revoked.

  • No provider key in the agent environment, image or docker inspect.
  • No MITM: LiteLLM is a reverse proxy for model APIs, not a TLS-intercepting forward proxy.
  • Pinned image digest, non-root, internal port only, provider keys from a read-only secret mount. A small Postgres on a separate internal network stores virtual-key and spend state; the agent cannot reach it.
04 Hardened image Dev environment
non-rootdigest pinschecksum installerread-only /etc/opencode

One opencode-dev target with the toolchain agents actually use. Hardening is in the build: digest-pinned base images, a checksum or signature-verified OpenCode install instead of curl | bash, no secrets in any layer or build argument, and a root-owned read-only system policy at /etc/opencode/opencode.jsonc.

  • OpenCode runs as the non-root agent user; no sudo.
  • Replace the system-wide safe.directory '*' with a scoped runtime GIT_CONFIG_* setting.
  • Remove the obsolete Dockerfile.new and fail a check if it reappears.
  • OCI labels plus SBOM/provenance in the multi-arch build target.
05 Launcher Hard boundary
cap-drop ALLno-new-privilegeslimitsinternal onlyfail closed

run.sh applies safe defaults: --cap-drop=ALL, --security-opt=no-new-privileges, --init, --pids-limit=2048, --memory=8g, --cpus=4, --ulimit nofile=1024:4096. It attaches only to opencode-agent, mounts host config read-only, keeps the repo read-write and state/cache in named volumes.

  • No ~/.ssh, no ~/.config/gh, no SSH-agent forwarding, no host.docker.internal by default.
  • Sets HTTP_PROXY, HTTPS_PROXY, NO_PROXY, BROKER_URL and LEASE_TOKEN; refuses to start if the stack health checks fail.
  • --with-ssh and --with-gh restore narrow exposure; --unsafe restores the legacy behaviour and warns.
  • --read-only adds tmpfs for /tmp and /run plus writable caches; opt-in for now.
06 OpenCode policy and plugins Inner guardrail
system policypermissionsguard.tsaudit.tslease.ts

/etc/opencode/opencode.jsonc holds hard policies and read-only permissions that a project cannot re-enable. Inside that, the guard plugin uses ctx.permission.hook("evaluate"), ctx.tool.hook("execute.before") and ctx.shell.hook("create.before") to block protected paths, dangerous commands and external directories, and to inject proxy environment variables.

  • audit.ts writes redacted JSONL to /var/log/opencode/audit.jsonl; it is a convenience, not tamper-proof evidence.
  • lease.ts looks up the lease and refreshes near expiry.
  • Project plugins, skills and MCP servers are allowed for trusted repos only when system policy approves them, and are audited. Explicit deny stays final.
  • --auto only suppresses prompts; it never relaxes a system deny.
07 Secret workflow Host-only
SOPS + ageKeePassXC alternativeno cloud

SOPS + age is the primary host store; a dedicated KeePassXC agent database is the alternative. scripts/opencode-secrets.sh resolves only the named values into the host-side stack environment. The agent never mounts the .kdbx, age key, decrypted file or provider root key.

  • No 1Password, Vault server or hosted manager is required.
  • Plaintext values do not land in the repository, image, compose files or shell history.
  • A pre-commit secret scan (gitleaks or detect-secrets) blocks fixture secrets.
What the inner layer cannot do

System policy, permissions and plugin hooks all execute inside the agent's trust domain. They raise the cost of an accident and catch obvious mistakes; they do not stop a determined process in the container. The hard boundary is the network plus the runtime.

05Three request paths

Model, git and packages take different doors

Every outbound need has a named route. Model traffic goes through LiteLLM, GitHub through the lease broker, generic package traffic through Squid, and direct egress does not exist.

OpenCode calls LiteLLM with a per-lease virtual key (sk-lease-…). LiteLLM validates the key, enforces the model allowlist, budget and duration, then injects the real provider key upstream. The agent never sees a provider root key, and no custom CA is involved.

OpenCode provider environmentbash
OPENAI_BASE_URL=http://litellm:4000/v1
OPENAI_API_KEY=sk-lease-...        # issued by the broker, expires with the lease
# provider root key lives in LiteLLM only
  • A revoked or expired virtual key is rejected by LiteLLM.
  • Model aliases in litellm.yaml keep provider names out of project config.
  • LiteLLM is dual-homed: reachable from the agent network, able to reach the provider.

The git credential helper and the gh wrapper ask the broker at call time. The broker mints or refreshes a GitHub App installation token scoped to the lease's repository and permissions. Tokens last about an hour; the lease can last eight. On a 401, the helper refreshes and retries.

Credential helper, at call timebash
# inside the agent: no ~/.ssh and no ~/.config/gh
git config --global credential.helper "!opencode-lease git-credential"
gh() { LEASE_TOKEN="$LEASE_TOKEN" command gh "$@"; }

# broker side: App JWT -> installation token -> lease scope
# installation token ~1h; broker refreshes while lease is active
  • The App private key stays on the host; the agent gets only the installation token.
  • After revocation, the broker mints no replacement; the agent needs a new approval.
  • The lease remains valid while the short-lived token rotates underneath it.

Package managers and general HTTP use Squid. The proxy checks the destination against a default-deny domain allowlist and logs the result. The agent's HTTP_PROXY settings make this seamless, but the internal network is what prevents a bypass.

Agent proxy environmentbash
HTTP_PROXY=http://proxy:3128
HTTPS_PROXY=http://proxy:3128
NO_PROXY=litellm,broker,localhost,127.0.0.1

# npm / pip / curl inherit the environment
  • Allow only the registries and destinations the project actually uses.
  • Squid cannot enforce HTTP method or path; service auth belongs to LiteLLM or the broker.
  • Allowed domains are still an exfiltration channel — keep the list short.

A process that ignores the proxy variables has nowhere to go. The agent is attached only to an internal: true network, with no default route, no host gateway and no default bridge. The connection fails before DNS or TLS.

Bypass test from inside the agentbash
# direct egress: no route, must fail
curl -m 5 https://example.com

# through the allowlisted proxy: must succeed
curl -m 5 -x http://proxy:3128 https://api.github.com

# host services and metadata: must fail
curl -m 5 http://host.docker.internal:11434
curl -m 5 http://169.254.169.254/latest/meta-data/
  • Test direct internet, host LAN, host.docker.internal, an allowed domain, a denied domain and the metadata address.
  • If any direct request succeeds, the network boundary is broken — fix it before shipping.
  • HTTP_PROXY is convenience, not enforcement.
Bypass test is the acceptance gate

docker/opencode/test/egress-bypass.sh runs inside the agent container. Direct internet, host LAN, host.docker.internal and the metadata address must all fail; the allowlisted host must succeed; the denied host must fail. A green suite is the proof that the network, not the environment, is doing the work.

06Credential leases

Approve a capability, not a secret

A lease is a scoped, expiring permission for one session to do one class of thing against one resource. It is not a cached PAT. The underlying credential can rotate while the lease stays valid, and revocation stops anything new immediately.

  1. Approve

    A human runs the lease CLI and grants a named capability: repository, actions and TTL. No secret is copied, and no host credential is mounted.

  2. Issue

    The broker records the lease and returns a bearer lease token. For GitHub, it signs an App JWT and mints an installation token scoped to the lease.

  3. Use / refresh

    The agent's helper fetches at call time. Near expiry, the broker mints a fresh installation token while the lease is active; no second human approval.

  4. Revoke / expire

    New token requests get 403 immediately. An already-issued installation token cannot be recalled; it dies at its roughly one-hour expiry and is not replaced.

Lease record

SQLite
lease_id
Random identifier; the bearer token references it.
session
The OpenCode session or job the lease belongs to.
service
github, litellm, or another broker-supported service.
resource
Repository or org, model alias or endpoint.
actions
Allowed operations, e.g. read, write, models:allowed.
expiry
Absolute TTL. Typical lease 8h; GitHub installation token ~1h.
status
Active, expired or revoked. Revocation is terminal.

Timing model

Refreshable
  • Lease TTL — how long the human's approval is valid. Default 8h, explicit per lease.
  • GitHub installation token — about 1h. The broker refreshes it on demand while the lease lives.
  • LiteLLM virtual key — model allowlist, budget and duration; rejected when the lease expires or is revoked.
  • Revocation — immediate for new token requests. In-flight tokens are not recalled.
  • Refresh failure — a clear 401/409 to the helper; the agent retries and the operator reads broker logs.

Lease CLI

Host-side approval and visibilitybash
# approve a capability for one repo, read/write, eight hours
opencode-lease approve github --repo owner/repo --actions read,write --ttl 8h

# show active leases: scope, TTL, last use
opencode-lease list

# revoke; new token requests fail immediately
opencode-lease revoke <lease-id>
Lease reuse is not PAT caching

A cached PAT is a long-lived secret that works until someone remembers to revoke it. A lease is a scoped approval with an expiry and a status the broker enforces. The GitHub token underneath it is short-lived and rotates; the lease token is the thing the agent holds, and it can be revoked without chasing the credential.

07Defence layers

Six layers, two of them structural

Each layer assumes the one above it may fail. The network and the runtime are the hard boundary; policy, permissions and plugins reduce the chance of a bad action getting that far, and audit tells you what happened.

01

Internal network + egress proxy

No default route; only the stack is reachable. Squid is default-deny with a short allowlist, no TLS interception, and logs. This is the layer that still works when the agent ignores every instruction.

Hard
02

Hardened image + launcher

Non-root, empty capability set, no-new-privileges, resource limits, read-only host config, no SSH/gh mounts, no host gateway, no Docker socket. Fail-closed when the stack is unhealthy.

Hard
03

OpenCode system policy

/etc/opencode/opencode.jsonc is baked into the image, owned by root and read-only. It outranks project and user config: a repository cannot re-enable a denied provider, tool or integration, and sudo is hard-blocked.

Policy
04

Permissions

Protected paths are denied (.env*, .ssh, key files, auth.json, vault files). Paths outside the workspace require explicit approval or denial. Shell stays usable inside the container boundary.

Policy
05

Plugin hooks

permission.evaluate, tool.execute.before, shell.create.before and session prompt/HTTP hooks enforce protected paths, dangerous commands and proxy environment injection. A hook may tighten a decision; it may never turn an explicit deny into an allow.

Inner
06

Audit

Proxy and broker logs are authoritative: timestamp, lease/session, destination, result, no bodies or secret values. The plugin audit log is a redacted convenience and can be tampered with by the agent.

Evidence
Hooks are not a sandbox

Every hook runs inside the process it is meant to constrain. A compromised or malicious agent, a project plugin with code execution, or a bug in the hook loader can bypass it. Never rely on plugin hooks to keep a hostile repo away from the host — that is what the internal network, the runtime flags and the absent mounts are for.

09Rollout

Four shippable phases

Each phase leaves the repo in a working state and can be rolled back without a migration. Reverting to --unsafe plus the previous image tag restores the legacy behaviour; the host-side stack is additive.

  1. 1 · Image + launcher

    One hardened target, safe default flags and the --unsafe rollback path. Image and launcher tests pass; the existing toolchain and worktrees still work.

  2. 2 · Network + proxy

    Create opencode-agent and opencode-egress, add Squid and the bypass suite. Direct, host and metadata requests fail; allowlisted registries work.

  3. 3 · Broker + LiteLLM

    Add leases, GitHub App token refresh and provider virtual keys. Remove root keys from the agent; prove revoked/expired credentials are rejected.

  4. 4 · Guardrails + docs

    System policy, guard/audit/lease plugins, OpenSpec strict validation, this SPA and the diagrams. Then run the full acceptance suite.

Rollback

Always available

Run with --unsafe and the previous image tag. The proxy, broker and LiteLLM are additive host-side services; stopping them does not alter the repo. “Safe mode is the default” remains a CI assertion.

No paid services

Constraint held

Every phase runs offline with local secrets. No hosted secret manager, paid sandbox or cloud broker is introduced at any point, and no phase requires a network service the host cannot run itself.

11Risks / non-goals

Where this design can still hurt you

The limits are documented rather than hidden. If one of these is unacceptable for the work at hand, the answer is a different isolation boundary, not a longer allowlist.

Risks and mitigations
RiskWhy it mattersMitigation
Shared kernel The container is not a microVM; a kernel or runtime escape reaches the host. Keep Docker updated, support rootless Docker, and use a microVM for hostile code. Do not call this kernel-level isolation.
Allowed-domain exfiltration Squid cannot stop data leaving to a domain you allowed. Keep the allowlist minimal; scope credentials with LiteLLM and the broker; treat egress logging as detection, not prevention.
Squid cannot enforce paths It sees host and port, not HTTP method or path. Use LiteLLM for model APIs and the broker for GitHub; add a reverse proxy or MITM only if a concrete path/method rule is required.
Custom broker code A bug in the broker is a credential bug. Keep it small, typed where practical, non-root with a read-only rootfs and dedicated state volume, and cover scope, expiry, revocation, refresh and log redaction in tests.
GitHub App setup More work than pasting a PAT; installation and permissions can be confusing. Document the App setup and keep a PAT fallback for a single job. The lease path remains the default.
Agent-tampered audit The agent can modify its own audit volume. Treat proxy and broker logs as authoritative; keep the plugin audit redacted and explicitly non-authoritative.
--unsafe becomes habit An escape hatch used daily is no longer an escape hatch. Print and log the warning, assert safe mode is the default in CI, and review --unsafe usage as an incident signal.
Project plugins are code An approved project plugin executes inside the agent. Trusted-repo assumption; audit plugin calls; deny integration.use for untrusted work. The boundary still has to hold.
Long-running refresh fails A job outlives a token and cannot renew it. Return clear 401/409, let the helper retry, keep the lease inspectable, and surface broker logs to the operator.

Explicit non-goals

  • Kernel-level or hypervisor isolation; use a microVM for untrusted code.
  • Paid or hosted secret managers, sandboxes or cloud brokers.
  • TLS interception or a proxy CA in the agent by default.
  • A general-purpose cloud credential leasing system in this change.
  • Replacing the existing audit/options SPA, or porting the Python Claude hooks.
